# Huurmonitor — local MVP

Personal Groningen rental review app, Dutch by default. React/Vite/TypeScript frontend, Node/TypeScript ingestion, private Supabase Auth/Postgres, optional Gmail SMTP digests (selected) or explicit Resend transport. The user has manually provisioned Supabase; read-only profile/table checks and anonymous denial succeeded. One explicitly authorized isolated Gmail test was SMTP-accepted; inbox receipt is separate. **The requested daily schedule activation is pending; this setup has not enabled scanning or sending.** `PRODUCT.md` records approved product constraints; the implementation decisions and current limits are below.

## Run locally

Node 22.12+ and npm:

```sh
npm ci
npm run dev
# Open http://127.0.0.1:5175/
```

The canonical local URL is **http://127.0.0.1:5175/**. Both `npm run dev` and `npm run preview` bind only to `127.0.0.1` on port **5175**, with strict port selection: if occupied, startup fails instead of switching ports. Run dev OR preview, never both at once. Preview serves the existing production build; it does not rebuild changed configuration. Keep Supabase Auth's local Site URL and allowed redirect URL exactly `http://127.0.0.1:5175/` (not `localhost` or another port). Email/password login stays inside the app; existing email-link callbacks can still be handled by the SDK.

No `.env` is needed for the explicitly labelled demo. Two public-observation examples demonstrate the application. Three Gruno JPEGs are local-review-only and excluded from Git because redistribution rights are unconfirmed; a fresh checkout uses the existing missing-image fallback. See `public/photos/PROVENANCE.md`. These observations are **not current rental recommendations**. Demo decisions and profile live only in `localStorage` under `huurmonitor-demo-v1`; delete that key to reset. No analytics, source reads, Supabase calls or email in default demo mode. Opening an original advertisement is an explicit external navigation.

```sh
npm test       # offline matcher/state/outbox and representative parser fixtures
npm run test:corrections # targeted state/parser/private-load regression evidence
npm run test:scan # focused inventory pagination, failure preservation, facts and matcher tests
npm run check # one TypeScript check of frontend + shared + worker + tests, then production build
npm run build
npm run worker # safely exits without contacting anything by default
```

## What works locally

- New / Favourites / Dismissed / Profile. Desktop selectable list + property detail; mobile property profile.
- Six-second photo stories within the selected home only, segmented progress, previous/next/pause controls; reduced-motion starts paused. Hidden/offscreen/press and focus within the gallery pause playback. Leaving focus resumes only if not manually/reduced-motion paused; no photo timer selects another home. No horizontal photo swipe was added.
- Deliberate horizontal drag on the **labelled title/header surface only** favours/dismisses. Vertical scroll, photos, description, links and buttons do not decide. Buttons perform every gesture action. Persistent Undo/Restore, visible focus and live decision announcements.
- Full descriptions, explicit price breakdown, utilities and unknown facts. One neutral saved profile drives matching; no assumed personal budget or income. Demo persistence is real browser storage, separate from cloud state.
- Property facts include explicit wijk, housing type, original move-in wording plus an ISO calendar date when unambiguous, advertising agency and separately disclosed landlord. Agency/source is **not** assumed to be the owner. Unknowns remain labelled; cached address geocoding is separate map metadata, never new profile criteria. Listing email/phone contacts are not collected.
- Source messages, cost breakdown and criterion explanations are always visible, not accordions. User rule: no decorative/useless disclosures; dropdowns only for functional selection (the profile's native selects).
- Existing-user Supabase email/password sign-in and private reads/profile/decisions are wired for manual cloud setup. No public signup or password-reset email flow.
- Conservative source discovery/detail parsers, failure-preserving reconciliation, meaningful-change events and transactional outbox code. These are **not proof of operational live delivery**.

### Metadata-only retroactive location maintenance

The separately approved **house-number fallback** is explicit opt-in:
`npx tsx --env-file-if-exists=.env worker/backfill-locations.ts --write --house-number-fallback`.
It targets only still-unlocated homes (maximum 38), never the previously located homes, and caps combined BAG/CBS work at 100 actual requests including any diagnostics. The original source title/address, suffix, postcode, `Listing.city` and all matching/business facts remain unchanged. Missing lookup city may use the user's explicit Groningen scope, recorded as `cityBasis: user-scope`, never promoted to a source fact. Versioned source/title/city/evidence binding separates this approval from legacy exact-address negative caches and invalidates changed inputs.

One complete base-street/house-number/city query is shared across unit titles, but each result is independently parsed/bound. An interpretable unique full-suffix exact match wins; otherwise only identical coordinates across **all** valid matching candidates allow a house-number-level point. All candidate BAG identities are retained (at most 50), with no nominated apartment, averaging, ranking or fabricated building/doorway claim. Differing points, incomplete result sets and unsupported/no-number titles remain unresolved. The map labels this **“Locatie op huisnummerniveau; toevoeging niet bepaald”**; identical points cluster while retaining separate advertisement IDs, titles, details and decisions. CBS coordinate/year work can reuse a validated classification but always rebinds its input identity. This supersedes the earlier exact-only/no-suffix-fallback restriction solely for this approved lookup mode; source points and legacy exact keys remain valid. The same serial pacing, transport stop, full-row CAS/oversize guard and exact before/after invariants apply; no automatic second pass or schema/RPC workaround.

With explicit owner authorization and no active monitor/delivery worker:

```sh
npx tsx --env-file-if-exists=.env worker/backfill-locations.ts --write
```

This standalone admin command reads **all** owner homes, including dismissed ones, and uses existing saved-address/BAG and CBS parsers. It never rescans sources, reevaluates persisted decisions, calls `apply_batch`, queues events, or sends email. Only `listing.addressEvidence`, `listing.geocoding`, and `listing.officialGeography` may change. Full-row JSON CAS prevents overwriting concurrent changes; conflicts and encoded URLs over 28,000 characters are skipped with no weaker fallback. Uncertain writes are read back without retry. Owner profile/config/version, source runs, events (including digest IDs), outbox, and full nonmetadata home state are compared in memory before/after; output contains aggregate counts only, with no private artifacts.

PDOK requests are globally serial, at least two seconds apart, with the existing 15-second/2MB response bounds. Ten-home batches share a 120-second deadline, the whole invocation allows 300 requests, and transport/parse failures stop expansion without retry. Existing positive/negative cooldown caches and inventory-wide address deduplication are respected. If an immediately preceding authorized diagnostic consumed requests, include them with `--prior-requests=N`. Validate one actual supported saved address against the existing parser before expansion; incomplete/ambiguous results are not positions. The BAG query uses escaped quoted street/city phrases and explicit fielded AND clauses (including supplied suffix/postcode), per [PDOK's documented Solr query semantics](https://github.com/PDOK/locatieserver/wiki/API-Locatieserver#22-gebruik-van-de-solr-q-parameter), rather than the default OR. Exact independent component comparison and complete candidate-set validation remain mandatory. Unsupported titles, room suffixes, missing confirmed cities and nonexact matches remain unresolved, never guessed. BAG is address-level, not a verified entrance; source coordinates remain authoritative; CBS classification is separate metadata.

This is a bounded maintenance pass, not a completeness guarantee or a deployment. An older deployed ingestion worker can erase enrichment on later observations until the map/enrichment feature is explicitly released. Refresh the signed-in GUI manually after readback; no release is implicitly authorized.

## Private cloud setup — manual setup and verification boundaries

1. Create your own **free** Supabase project only after deciding to proceed. Disable public signups; manually add one Auth identity. Do not use rental-source accounts.
2. Run `supabase/schema.sql` in that project's SQL editor once (fresh-project migration). Provision that identity's profile using the commented neutral-profile insert and its UUID. No personal profile values are pre-filled.
3. Configure Auth Site URL and the exact local allowed redirect URL as `http://127.0.0.1:5175/`; add the final Pages URL only after separate execution authorization. The same existing owner identity must have a password; see the prerequisites below. Routine password login needs no SMTP or Auth email-template update.
4. Copy `.env.example` to `.env`. For private browser data set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (prefer `sb_publishable_`; legacy `anon` JWT allowed). Other Supabase key types are rejected by the browser helper. The separate optional public `VITE_CARTO_BASEMAPS_KEY` is described below. **Never put a service-role/secret key in a `VITE_*` variable, frontend code, Pages assets or repository history.** Restart Vite after changing configuration.
5. Sign in using the existing owner's email and password in the app. Actual password login has not been executed during development. Missing provisioned profile/RLS/schema shows a recoverable error, not sample private data.
6. Read-only worker access to the provisioned owner profile/five tables and anonymous read denial have passed, and all five RPCs appear in metadata. Still verify authenticated browser owner-only reads, second-user isolation and concurrency before relying on them; metadata is not RPC execution proof. No account creation, SQL mutation or schema migration is performed by the scan command.

RLS is enabled on every browser-visible table. Authenticated users have owner-only SELECT; direct table writes are revoked. Only `save_profile(config)` and `set_decision(key,decision)` are browser-executable security-definer functions, bound to `auth.uid()`. Worker RPCs are service-role only with a fixed empty search path. The backend key must be scoped operationally to this personal project and explicitly targets `OWNER_USER_ID`.

Private profile/state never enter the static bundle. Supabase's session token is stored by its browser SDK; do not use a shared browser session. Sign out before lending a device. Auth/mode/unmount boundaries invalidate pending private loads synchronously; late responses cannot render in demo or enter demo localStorage. Newer refreshes also supersede older loads. Private profile/decision completions are scope-guarded too. Refresh reloads cloud changes from another device. Realtime subscriptions are not included.

Supabase Free may pause after one inactive week and has **no free backups**. Arrange your own private exports/recovery before relying on it. Data deletion: remove the Auth owner to cascade profile/home/event/outbox rows, and remove local demo storage independently. No backup, paid plan or automated export has been configured.

Archive search includes current validated official names as well as source wording.

Generic label/value collection keeps the **first occurrence**, including an empty value; identical repeats change nothing. This does not disable Gruno's dedicated financial conflicts, coverage, contradictory availability or ambiguous-date safeguards. This is bounded representative extraction, not a claim to extract every provider field/template. Existing queued payloads remain immutable snapshots: rendering never joins/rebases current homes or starts geocoding. Older snapshots without valid geography honestly remain unresolved.

Worker-only PDOK requests send the supported address evidence, not the owner/profile; they do **not** run on browser navigation.

Otherwise a matched PDOK/BAG result is usable only for the exact current normalized street, house number, letter, addition, city and optional postcode. Inputs deduplicate across stored homes. Serial 2-second spacing, 15-second request/stream timeout, 2 MB streamed body cap, no redirects/retries, at most 10 address queries and a shared 120-second address/CBS pass deadline bound work. Transport failure stops further uncached pass requests without cooling unattempted homes; generic counts only are logged. These limits are client precautions, not a provider SLA.
